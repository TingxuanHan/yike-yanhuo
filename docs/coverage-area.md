# 连续设施覆盖分区

2026-10-16。对应百度任务书“功能正确性与覆盖率40%”中的1公里民生设施缺口，以及“API深度调用与工程优化30%”中的结果复用。不是以更多生活功能替代地图核心验收。

## 使用流程

Web：打开社区体检 → 体验模拟社区或导入已有报告 → 设施核查 → 选菜市场、药店或小学。地图显示连续候选缺口和待核查区域，下方给出三类面积；原有采样点仍可查看最近设施和检索依据。导出的分区JSON含完整原报告、类别、时长、算法版本、局部米制坐标及多边形，可离线重算。报告同时汇总三类设施面积。

微信：社区体检 → 设施核查 → 同一类别选择器。连续分区、面积和折叠依据共用Web算法，支持复制带来源说明的摘要。示意图不是导航底图；带孔洞的区域仅画边界，避免原生旧Canvas填色抹去孔洞。大字模式把面积与名称分行。无需购买云资源即可运行离线示例；跨网络数据互通仍需共同后端。

## 三类面积如何得到

| 状态 | 计算依据 | 可以怎样解释 |
| --- | --- | --- |
| 已找到设施 | 已有步行轮廓与可用同类设施1公里内近似区域相交 | 当前已检索资料中有同类设施，未证明营业、入口或现实可通行 |
| 候选缺口 | 位于所有1公里外边界之外，类别返回结果已取完，且该位置完整1公里核查范围包含在检索范围内 | 本次资料支持的候选缺口，仍需台账及现场核验 |
| 待核查 | 剩余区域；分为距离边界保留带、检索边界不足、类别未取全 | 不把缺少证据解释为当地没有设施 |

“覆盖”使用直线距离，与“从出发点走到设施的路线用时”分别统计。即使设施不在步行圈内，或中心至设施的路线耗时未知，只要它的有效位置可以解释圈内某点的1公里邻近关系，就仍参与覆盖计算。排除已停用及存在核查冲突的设施，不将私人地点自动混入公共设施。

距离圆使用128边内接/外接近似并留1毫米数值余量。1公里门槛的几何保留带最宽约0.604米，保留为待核查；这个数字**不包含**地图坐标误差、局部投影误差、关键词漏检和路网插值误差，不能宣称现实距离精度为0.604米。检索完整区域使用保守内边界，可能增加少量待核查面积。分类区域互斥，合计面积等于所选已有步行轮廓；保留孔洞与断开的片区，不把凸包或采样点方格填成区域。

空轮廓不给面积结论；轮廓可能截断时只统计已有部分并提示。计算失败清除旧分区、保留原始点位依据，不把上一个类别的结果留在地图。面积是几何面积，不是人口覆盖率，也不是到店步行距离。

## 工程与验证

- 只复用已有报告，不增加地点检索、坐标转换、路线或底图调用。先用包围盒剔除不会相交的设施，精确坐标去重，再分批合并；不截断不同地点。
- Web与微信编译同一核心，不增加依赖；微信单次数据更新超过900KB时显示错误并保留点位核查。
- [固定构造验证](experiments/coverage-area-simulation.md)：4种情况、23,428个独立偏移网格点。错误已覆盖、错误候选缺口、未分类点均为0，面积守恒误差小于0.001平方米。只验证构造几何，不等于真实POI或街道准确率。
- [历史上海回放](experiments/coverage-area-shanghai-replay.json)：2026-10-05记录的15分钟轮廓约1.761平方公里，三类设施在当前数据中均有完整面积的正向覆盖证据，没有发现候选缺口。类别本身未取全，因此不能把结果说成完整设施普查；“未取全”不否定已找到的邻近设施。没有新百度请求或新增现场核验。
- 新增5项几何测试、2项微信页面业务测试和1项浏览器流程；检查孔洞、边界、检索不全、圈外设施、停用、去重、时长、异常清除、导出、320/390像素无横向溢出。原生微信CLI验证标准/大字渲染；新增手机实走验收待完成。

## 后续验收顺序

1. 用真实社区台账核对设施漏检、入口与营业状态，保留未找到、分歧和已停用样本。
2. 在多个中心做预先固定的独立路线点与现场计时，分别评估路网范围和设施缺口，不能混为一个准确率。
3. 验证新增微信页的实体手机与弱网恢复，再扩大到共享后端试点。

不为此功能增加实时红绿灯、跨账户跟踪或未经证实的自动障碍绕行承诺。
