# 设施数据清洗与多源合并策略

当前运行数据来自百度六类关键词检索。已实现单来源清洗、去重、分类、步行统计和完整性标记，以及针对已有设施的多来源核查记录导入。尚未采集社区台账等第二来源的真实材料，不将软件支持能力描述为已完成多源实证验证。

## 当前实现

1. 检查经纬度有效性并转为社区尺度局部坐标；过滤检索半径外及缺少名称的条目。
2. 医疗关键词映射为社区卫生服务中心，养老映射为养老服务；原始关键词召回不能直接等同于精确分类。
3. 同类别UID相同则去重。UID缺失时，名称做NFKC、空白及常见符号规范化，再按30米距离判重。
4. 不同UID的同名分店保留，不跨类别自动合并。无效条目会使完整性标志失效。
5. 每类仅在总数明确、分页取全且无无效条目时标记本次返回完整；数量上限和检索遗漏保持可见。
6. 设施是否在圈内以步行耗时判定；未知路线不计入可达设施，但在明细中标记待核实。

对应实现：`src/server/baidu.ts`、`src/core/facilities.ts`。契约测试涵盖缺少总数、分页截断、非法位置、同名分店和缺失UID。

## 已实现：设施核查台账

在体检报告的“设施核查”中，选择已有设施，填写来源名称、来源内编号、核查时间、可用/停用/待核查结论和具体依据。也可下载JSON模板，填写后导入预览，再显式应用。支持撤销上一次操作；保存报告或导出JSON后保留全部核查记录，打印附录保留来源与依据。所有操作在浏览器本地进行，不调用地图接口。

来源名称和来源内编号共同确定记录身份。同一来源编号使用时间最新的记录判断状态，同时保留历史版本；同一时刻结论矛盾、或不同来源结论不同，标记“来源冲突”，不以较新来源静默覆盖旧来源。同名但编号不同的记录不会自动认定为同一来源条目。

停用、待核查或来源冲突的设施暂不计入设施数量和覆盖，原设施坐标与路线测时保留。相应类别的检索完整性保守降为不完整，不能以排除一处设施证明整片区域没有设施。未核查的地图记录仍按原检索结果计数，报告明确标记未核查；确认记录只表示使用者提供了依据，不等于平台独立认证。

文件格式为`yike-poi-evidence-v1`，绑定`resultId`，每条使用当前报告的`facilityId`关联；字段包括`source`、`recordId`、UTC ISO格式的`checkedAt`、`status`和`basis`。单次最多500条、500KB，每处最多30条历史依据。错误报告编号、未知设施、缺失来源或依据、超限均拒绝整批导入，原报告保留；未知扩展字段丢弃。模板仅供填写，空模板不能直接应用。

这一步支持“已有设施的多来源核查”，尚不支持自动匹配第二来源的新设施、坐标迁移、类别修正或新设施测时。新设施进入统计前仍需完成下述坐标与去重流程。

## 第二来源接入时的字段与判断

社区台账、人工核验和地图POI应保存来源名称、来源内ID、采集时间、名称、类别、坐标系、位置、地址、营业/开放状态和核验依据。每个来源的ID只在其自身命名空间内有效，不能跨供应商直接用相同UID合并。

先统一坐标系，再生成“同类、近邻、相似名称”的候选匹配；30米仅作初筛。入口不同、同楼不同服务、名称相似但不同分店应人工确认，原始来源记录保留，不静默覆盖坐标或营业状态。相互冲突的状态在报告中列出“待核验”，不能只保留更有利的一条。

补录设施只有具备有效测时后才进入5/10/15分钟统计。确认一个设施存在可以支持该点的覆盖判断；零星补录不能让整类检索变成完整，更不能以台账中没有某设施证明现实中没有。

## 待采集的证据

至少抽查菜市场、药店、小学各数处，核对入口、标签与营业状态；保留每条合并/保留决定及来源日期。样本未采集前，不报告分类准确率、召回率或多源去重收益。
