# 多条件补点与绕行核查

对应百度任务书的路网可达范围、设施缺口、工程复用与可解释报告。两项能力从已有体检报告继续计算，Web与微信使用同一核心，无需新增地图、模型或语音请求。

## 赛题问题与实现增量

任务书提出，道路绕行和过街等待会使“直线距离近”不等于“15分钟走得到”。已有轮廓给出可达范围，但还缺少可带去核查的绕行线索；已有补点比较给出单个条件下的收益，但不能说明步速、出发时刻或等待假设改变后，选择是否仍合适。

因此增加“看起来很近，为什么要走更远？”和“换种走法，方案还合适吗？”，延伸社区体检，不增加日常首页入口。参考[Conveyal情景对比](https://docs.conveyal.com/analysis)对不同假设分别计算可达性的思路，未复用其代码、数据或界面，也未引入其公交概率和分位数模型。最小化最大后悔值是已有决策方法；本项目的增量是将其接入有限路网采样、缺口与未知分离、双端交互及可复算导出，不据此声称算法全球首创。

## 操作入口

Web打开`/?showcase=1`，选择“体验模拟社区”，进入设施核查：

1. 展开“看起来很近，为什么要走更远？”，先看前三处线索；可展开到八处，查看现场核查坐标或导出完整依据。
2. 在“设施补点方案比较”选择类别和一至三处已有测时位置，完成原有方案比较。
3. 展开“换种走法，方案还合适吗？”，点击“检查三种条件”。默认第二组步速为原步速的75%，第三组另设每公里两处、每处30秒等待；参数可改，均是假设。
4. 按新增一处／两处／三处选择方案，查看最大落后面积、三组共同补足区域，以及逐组的范围、缺口和未知。
5. 导出依据，使用下方命令独立复算。修改条件、候选位置、类别、时长或报告后，旧比较失效；输入错误保留草稿。

微信入口为“附近 → 社区体检 → 设施核查”，支持标准和大字模式。微信复制摘要与核查清单，Web导出完整JSON。演示退出恢复原页面与报告，临时比较不覆盖地点簿或私人偏好。

## 多条件比较的计算

| 条件 | 用时计算 |
| --- | --- |
| 原步速与时段 | 已有路线距离 ÷ 原步速，加原等灯假设 |
| 对照步速与时段 | 已有路线距离 ÷ 对照步速，沿用原峰谷规则 |
| 对照步速＋设定等灯 | 对照步速，改用设定的路口密度和每处固定等待 |

三组均重新经过个人试算与轮廓计算，不把原API总耗时按步速缩放后再次加灯时。原报告和原始耗时保留。未启用峰谷等待时，仅改出发时刻不会改变范围；启用时按假定抵达路口时刻计入等待，前次等待影响后续抵达。第三组固定等待，不声称知道实际红绿灯周期。

设同一新增数量的方案为`p`，条件为`s`，新增覆盖的**已知候选缺口面积**为`G(p,s)`：

```text
条件最好收益 B(s) = max G(p,s)，只取相同新增数量的候选方案
方案最大落后 R(p) = max_s [B(s) - G(p,s)]
比较顺序：R(p)较小者优先
三组共同补足区域 = 三组新增缺口覆盖区域的空间交集
单组最少补足 = min_s G(p,s)
```

共同补足与单组最少补足不同：三组可能覆盖不同位置，不能用最小面积冒充同一片区域。共同区域取交集，仅部分条件计入的区域取并集减交集；灰底为三组分析范围并集。各组范围、原缺口和未知单列，不比较不同分母的百分比。

最多三处候选产生七个组合，一处只与一处比较、两处只与两处比较。只有一种组合、没有已知收益或三组设置相同时，不给出有意义的优劣推荐。相差不足0.001平方公里提示接近，这是展示尺度，不是统计等价或现实精度。空范围条件仍计入、收益为零；重复条件不多投一票。

取舍按绝对面积计算，没有人口、年龄、土地成本或服务容量权重。若重点服务慢行人群，应看该组收益，不能将总体最大落后较小解释成对每个人最好。只枚举所选位置，不是全局选址优化；候选点在较慢条件下落到圈外仍作为设施位置假设参与，必须另查入口和可建设性。

设施影响范围复用[连续覆盖分区](coverage-area.md)与[补点比较](facility-siting.md)的距离口径及保守边界，不是从新设施出发的实际路线服务区。未知的假设覆盖单列，不计入已知缺口收益。现实建设、商户接入、容量和可用性都没有被模拟结果证明。

## 绕行线索的计算

读取已有设施与采样点的路线长度和耗时。同坐标去重，优先显示可用设施名称；明显距离／耗时分歧或同时有可达和未连接记录时，单列记录分歧。缺测、未连接与异常距离分别计数。

“步速×所选分钟数”给出**不计等灯的直线对照半径**，只筛选附近已有点，不将该圆当作等时圈。距离出发点不足80米的点排除，避免小分母放大倍数。有效点同时满足以下门槛才生成线索：直线至少80米、路线至少多200米、路线达到直线1.5倍。

门槛用于安排核查次序，未经真实障碍标注校准。默认列三处、最多八处，按额外距离排序；导出保留全部线索与原报告。原始报告耗时与个人试算耗时明确标注。超时点数不等于绕行点数，前者还可能受等待或步速影响。

没有路线形状、入口照片或实测依据时，只能指出值得核查的位置，不能推断围墙、河流、施工或具体路口原因，也不能生成捷径。端点吸附、坐标误差和记录年代均可能影响结果。点数不代表面积、人口或发生率；没有线索不等于没有障碍。

## 固定构造对照

[完整输入与输出](experiments/planning-evidence-simulation.json)含两组人工场景和四份导出回放结果，均可重建。

第一组复用默认模拟路网：116个直线对照范围内有效点、21条绕行线索；三处候选、三条件、七组合。第二组特意构造直线径向距离及一处已有小学，用于检验排名变化，不是上海社区。路线等于直线距离，绕行线索为零；缺口距离改为400米仅用于此构造对照，不能冒充任务书1公里口径。

第二组增加一处的新增已知缺口覆盖面积，单位平方米、展示取整：

| 方案 | 原步速1.2米/秒 | 对照0.5米/秒 | 对照步速＋等待 | 最大落后 |
| --- | ---: | ---: | ---: | ---: |
| A | 443,564 | 7,407 | 6,757 | 28,058 |
| B | 305,944 | 35,465 | 33,483 | 137,620 |

原条件A收益较大，后两组B收益较大；最大落后口径仍优先A。这展示了取舍，不证明A更适合慢行用户，也不是建设推荐。测试检查同数量比较、空间交集、未知不计收益、空范围、重复条件、原报告不变及导出篡改。

## 工程与复现

核心为`src/core/siting-conditions.ts`、`detour-audit.ts`和`planning-evidence.ts`。React与微信复用计算；微信仅向`setData`传紧凑视图，完整报告留在控制器。无新增依赖，不修改串行网关、并发或额度，不回写原报告。

```sh
npm ci
npm run build
npm test
npm run test:ui
npm run benchmark:planning
npm run verify:planning -- .cache/planning-evidence/0-siting.json
npm run verify:planning -- .cache/planning-evidence/0-detour.json
```

历史真实报告可用`npm run benchmark:planning -- /path/to/report.json`，只读文件、不发请求。构造输出在`.cache/planning-evidence/`，源码固定记录在`docs/experiments/`。

导出含原报告、版本、条件和候选位置。复算重建逐组面积、结论及几何对称差；0.001平方米为计算一致性容差，不是现实精度。绕行复算核对点、距离、计数与排序。浏览器实际下载文件交给Node复算；篡改来源、条件、坐标、面积或形状会被拒绝。如果同时篡改输入与结论，复算不能证明输入来源可信。

## 百度评分对应

| 维度 | 本轮补强 | 边界 |
| --- | --- | --- |
| 正确性与覆盖率40% | 路网与直线差别、同候选多条件缺口、未知独立、空间交集 | 不推断障碍原因，不把假设当实测 |
| API深度与工程优化30% | 复用距离、轮廓与报告，双端共享，离线复算 | 零新调用，不声称增加真实样本 |
| 交互体验15% | 沿核查流程折叠展开，先结论后依据，窄屏与大字 | 模拟器不等于手机实走 |
| 开源工程15% | 固定反例、历史摘要、测试、版本及复现命令 | 访问权限和正式提交另行处理 |
