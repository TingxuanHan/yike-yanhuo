# 技术设计

## 用户流程与结构

选择分析中心 → 获取周边设施 → 测量步行耗时 → 生成可达范围 → 检查设施覆盖 → 导出体检报告。

前端使用 React、TypeScript 和 Vite，后端使用 Node.js。前后端共享明确的数据类型，空间计算不依赖界面。地图服务通过提供者接口替换，离线模拟与百度实测走相同的分析流程。

## 坐标与可达范围

分析内真实坐标统一为 BD-09 经纬度，经度在前；百度 Web API 参数按其要求转换为纬度在前。私人地点簿按来源保留BD-09、GCJ-02或WGS84声明；GPS 或 GCJ-02 输入经官方坐标转换服务转换后再进入分析。

第一版采用规则网格采样，并在阈值附近局部加密。每个采样点保存实际路线耗时或明确的未知状态。把网格拆成三角单元，使用阈值插值得到多片区轮廓，不使用凸包跨越未知区域。边界属于近似结果，不保证每个插值位置都可通行；现场障碍和出入口仍需核验。

采样范围必须记录；等时圈触碰范围边缘时报告“范围可能截断”，不能把采样边界解释为自然步行边界。5、10、15分钟使用同一批观测计算，减少重复调用。

## 设施与缺口

按菜市场、药店、小学、医疗、公园、养老六类组织设施。优先使用稳定 UID 去重，缺失 UID 时使用规范化名称、分类和位置近邻判断。百度分类和其他来源标签需映射到同一分类表。

圈内设施根据中心到设施的步行耗时统计。缺口则按网格点周边1公里的分类设施覆盖检查，明确这是距离口径，不等同于15分钟步行口径。检索分页截断、请求失败或返回上限触发时，仅给出“待核查区域”，不声称当地确实没有设施。

## 请求与资源控制

服务端 AK 只保存在本地环境中；浏览器地图使用独立的浏览器端 AK。服务端固定上游域名、验证输入范围、限制同时运行的分析和单次路线预算。

批量算路按路线条数计费和限流。按账户的路线 QPS 切分批次，不能以请求数量代替路线配额。设置超时、有限重试、请求内去重，以及有界的短时缓存；默认不落盘保存第三方原始地点数据。

## 结果证据

报告保存模式、输入、算法参数、来源、生成时间、采样完整性、设施检索完整性、调用统计和限制。示例数据标记为合成；没有实测时不生成真实社区性能数值。

## 第一版范围

交付网页工作台、分析接口、样例道路图、设施分类、范围计算、缺口提示、导出和测试。人口加权公平性、规划选址优化、施工围挡实时感知、无障碍专用导航暂不承诺完成。

## 日常出行扩展

Web增加私人地点簿、老人协助指引和5—30分钟个人试算；微信原生开发版复用业务契约与服务。共享数据写入SQLite，客户端显式配对与手动同步，版本冲突保留本机草稿。两端试算调用同一核心实现，按路线距离、步速和人工信号等待假设计算，不复制地图计费逻辑；现有串行限额保持不变。完整设计与尚未完成的实测、真机和发布环节见[日常出行与双端设计](daily-life-design.md)。
