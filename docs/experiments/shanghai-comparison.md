# 上海候选入口：24点步行对照实验

日期：2026-10-05，北京时间11:10固定验证方案，11:11完成测量。候选中心为四平路街道抚顺路社区睦邻中心的地理编码点，实际入口尚未现场核验。

本次复用10:17保存的133点分析结果；没有重新检索POI，也没有用验证点重建轮廓。摘要见[机器可读结果](shanghai-summary.json)。原始设施、测时坐标和完整观测仅留在本地忽略目录，未作为开放数据发布。

## 固定协议

- 以中心为原点，半径250、600、1000米，每圈8个点。
- 角度为从正东逆时针22.5°起，每45°一点；局部坐标保留毫米。
- 所有验证点与既有采样点及设施测时点至少相距10米。
- 三种方法使用相同中心、5/10/15分钟阈值与相同24点：直线圆假设1.2米/秒；400米规则网格复用81个旧采样点；现有边界加密轮廓复用133点。
- 参考值为新调用的百度步行矩阵结果。未知路线单独计数并排除一致率分母，本轮24条均有效。
- 评价“点在预测范围内”是否与“API耗时不超过阈值”一致。保留孔洞和分离片区，不以包围盒判定。
- 这是同一接口的留出点验证，不是独立地图供应商或现场步行真值。三个阈值共用同一24点，不能视为72个独立样本。

## 完整结果

| 方法 | 网格点数 | 阈值 | 正确可达 | 误判可达 | 漏判可达 | 正确不可达 | 一致率 |

| 400米规则网格 | 81 | 5分钟 | 0 | 0 | 3 | 21 | 21/24（87.5%） |
| 边界加密 | 133 | 5分钟 | 0 | 2 | 3 | 19 | 19/24（79.2%） |

| 边界加密 | 133 | 10分钟 | 8 | 0 | 1 | 15 | 23/24（95.8%） |
| 直线圆 | 0 | 15分钟 | 16 | 8 | 0 | 0 | 16/24（66.7%） |
| 400米规则网格 | 81 | 15分钟 | 14 | 0 | 2 | 8 | 22/24（91.7%） |
| 边界加密 | 133 | 15分钟 | 15 | 0 | 1 | 8 | 23/24（95.8%） |

15分钟加密轮廓在本样本优于直线圆，较规则网格少漏判1点；10分钟与规则网格相同。5分钟加密轮廓表现更差，3个实际可达点全部漏判，并多出2个误判可达点。因此不能声称“加密全面提高精度”。

5分钟短范围更容易受到入口位置、网格间距和路线时间非线性的影响；这是待进一步验证的原因假设。下一轮改进应先核验中心入口，再固定近中心的新验证点，不能复用本轮24点调参后把同点提升当作独立验证。

## 调用与运行证据

新增24个请求 / 24条路线，0次检索，0次重试；最短实际发送间隔1104毫秒，任意滚动一秒最多1次路线请求。测量采用单个串行队列，预览服务在测量前关闭。

完成后的项目本地日计数：路线216/500、地点检索6/12、其他服务5/50、地图资源转发43/500。地图资源转发数不是平台计费单位，计数不包含其他项目和机器。

原分析耗时来自降速前的记录，不能与本次1条/1.1秒的设置作效率比较。这里只对比几何预测和采样点数，没有宣称端到端性能加速。

## 复现

离线命令：`npm run benchmark:demo`。人工构造路网结果写入`.cache/benchmark-demo.json`，不消耗配额，也不能替代上述上海结果。

重新开展真实实验前需要已有`.cache/live-result.json`；先停止真实预览服务，再运行：

```sh
node --import tsx scripts/benchmark.ts --plan
node --env-file=.env --import tsx scripts/benchmark.ts --live
```

计划保存原结果SHA-256和固定24点，实测前再核对。已有计划或观测时脚本拒绝覆盖式重复实测；不要为再次录制界面而清理这些文件。每完成一个观测立即保存，异常即停。总路线预算为24，包含重试，不会因单点失败突破预算。
